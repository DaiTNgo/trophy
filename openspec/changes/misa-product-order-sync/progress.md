## 2026-08-09 SaleOrder presence-check correction

- Confirmed against the configured MISA tenant that a successful `POST /SaleOrders` returns the created numeric ID in `results[].data` (for example `9663`). MISA SaleOrder lookup requires the plural query parameter `GET /SaleOrders/id?ids=9663`; the earlier `id` parameter returned a misleading HTTP 200 response without data. Lookup by `sale_order_no` can also return `data: []` for the same record, so the persisted MISA ID is the authoritative reconciliation key.
- Checkout now extracts and persists `results[].data` as `orders.misa_sale_order_id`, and creation errors are no longer swallowed. The automatic Order Detail presence check uses the persisted ID with `ids`, and marks an order `missing` only for an explicit MISA HTTP 404. Existing `missing` orders which retain an ID are checked again when opened, allowing false negatives to self-heal. The structured log `MISA SaleOrder presence check` records the local order ID, MISA ID, and whether the API supplied data, without logging shopper payloads.
- Verification: `pnpm --filter backend test -- --run src/lib/misa.test.ts`, `pnpm --filter backend test -- --run src/routes/admin/orders.test.ts`, backend typecheck, and backend build pass (219 tests).
